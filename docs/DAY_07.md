# Day 7 — Vehicle tracking and controls

## Scope

Cars now has All cars, Tracking and Problematic views. Car details also include a GPS route map with independent loading, empty, error and refresh states. Vehicle status supports optional 10-second auto-refresh. Tracking uses Leaflet with OpenStreetMap base tiles. Vehicle positions, labels, fuel and routes come from the local backend, not fixtures. The vehicle selector also provides an alternative to clicking map markers.

Manual refresh is available. Optional auto-refresh waits 10 seconds after each tracking request finishes, skips hidden tabs, and cancels its timer and request on unmount. GPS history has a separate refresh action. Failed refreshes identify retained positions as the last successful snapshot.

## Verified contracts

All requests use the existing cookie-based API wrapper.

| Endpoint under `/api/admin` | Use |
| --- | --- |
| `GET /cars/tracking` | Active vehicle positions, status, connectivity, speed and fuel |
| `GET /cars/:id/gps-points` | Timestamped latitude/longitude points |
| `GET /cars/:id/status` | Engine, doors, online state, speed, fuel and rental ID |
| `GET /cars/:id/last-activity` | Event and last activity timestamp |
| `GET /cars/commands` | Supported command codes and labels |
| `POST /cars/:id/send-command` | Send `{ command }`, then reload status |
| `GET /cars/problematic` | Cars with the backend's `issues` array |
| `GET /cars/:id/toggle-active` | Confirmed availability transition, followed by refresh |

Authenticated curl reads were used to inspect tracking, GPS history, status, last activity, commands and problematic cars. Response shapes were also checked against backend source. Coordinates, IDs, booleans, dates and numeric ranges are validated before use. Problematic cars reuse the shared table with search, issue filtering, sorting and pagination.

## Mock behavior to understand

- Tracking returns active cars; inactive cars are not invented on the map.
- GPS history is generated by this mock per request, not a durable recorded trip. Its zigzag shape is not evidence of real driving.
- Commands offered by the backend are lock, unlock, engine_on, engine_off, horn and locate. Only engine commands change engine state in this mock; door lock state is derived from engine state. The UI says “Command accepted” and reloads authoritative status rather than inventing a successful lock transition.
- Toggle-active is a mutating GET in the supplied backend. It is only called after explicit confirmation, with no caching, polling or automatic retry.
- The simulator can change rentals and fuel independently of frontend actions.
- UI permissions restrict controls to `cars.edit`; real authorization must also be enforced by a production server.

## Map choice and safety

[Leaflet](https://leafletjs.com/reference.html) is sufficient for markers and polylines without an API key. Popup values are assigned through DOM text content, not HTML interpolation. Map instances, observers, layers and request timers are cleaned up.

Leaflet expects `[latitude, longitude]`; reversing them changes the location. Points are sorted by timestamp before drawing. Marker colors prioritize offline state, then low fuel, then rented/available status.

[OpenStreetMap's tile policy](https://operations.osmfoundation.org/policies/tiles/) requires attribution and responsible tile use. Attribution stays visible; there is no bulk download, prefetch or cache bypass. Tile requests disclose the viewport and client IP to the tile provider, but car labels and route payloads are not sent there. Production deployment should select a provider appropriate to its traffic and privacy requirements.
